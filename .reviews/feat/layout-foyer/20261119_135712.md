## Vue d'ensemble

Depuis l'itération 1, le compte est créé en console sans foyer, le foyer se crée dans l'app (`Households::Create`,
redirection quand l'utilisateur n'en a pas), un utilisateur peut avoir plusieurs foyers, et le foyer actif est mémorisé
en session et lu via `policy_scope`. L'autorisation est explicite, le foyer d'un autre donne une 404, et les clés I18n
sont complètes. Le code est correct ; un seul point de couverture.

## Conclusions

### [medium] La spec de création ne prouve pas que le nouveau foyer devient actif

**Fichier**: `spec/requests/households_spec.rb:31-32`
**Problème**: `include("Zébu", "Foyer « Zébu » créé.")` passe même sans `session[:household_id] = household.id`, car
« Zébu » figure déjà dans le message flash. Le foyer par défaut (« Appartement ») pourrait être affiché sans que la
spec échoue.
**Impact**: une régression sur le comportement annoncé (« le foyer créé devient le foyer actif ») passerait inaperçue.
**Suggestion**: vérifier le foyer affiché hors du flash, par exemple `not_to include("Appartement")` ou le lien du nom
du foyer.
**Statut**: corrigé (`not_to include("Appartement")` ; la spec échoue bien si l'on retire la mise en session).

Points examinés et écartés :
- `include Dry::Monads[:result]` expose `Success`/`Failure` dans `action_methods` des contrôleurs : aucune route ne
  les vise.
- `session[:household_id]` survit à la déconnexion : ignoré par `policy_scope` pour un non-membre, aucune fuite.
- Requêtes supplémentaires dans `households#index` : négligeables à l'échelle d'un foyer.
- Assertion `not_to include("Foyer d&#39;un autre")` dépendante de l'échappement : correcte aujourd'hui, le scope est
  aussi couvert par la spec de policy.
- Rollback de `Households::Create`, tâche `accounts:create` et paramètre absent (400) sans spec : comportement de
  Rails, ou outil console.
